## 1. 设计动机：两套机理分明

KirinNet 用**两套机理**防投毒/防污染，本文件管**第一套（引导期，中心化式、一次性阀门）**：

| 机理 | 定位 | 时段 | 机制 | 文件 |
|---|---|---|---|---|
| **引导期计数（本文件 T8）** | 防投毒（域名发布投毒） | 引导期（一次性阀门） | 计数泛洪 → 1000 万阈值 → 共识时间戳 → 开关传播 → 计数关闭永不返回 | **本文件** |
| **运营期信任权重（T3）** | 防污染（社交信任） | 运营期（持续机理） | 信任权重（min 保守聚合 + -127 黑名单）去中心化防污染 | **T3** |

**切换点（共管）:** 共识时间戳触发全网开关 → 计数关闭（T8）→ 信任权重接管（T3）。切换点由双 PM 共管（KNET-COM-03），本文件定义触发条件与 fail-closed 默认值，不单边裁定切换时机。

**去中心化纪律:** 引导期计数是**一次性中心化式阀门**（计数达阈值后全网一致关闭），**不违反**「不依赖中心化权威」—— 它是引导期临时手段，运营期完全由去中心化信任权重（T3）接管。

## 2. 计数包语义（count payload）

### 2.1 节点本地计 1 还是回执聚合？（明确：**本地计数 + 回执聚合**）

**结论（草案）:** 采用**本地计数 + 回执聚合**双轨：

1. **本地计数:** 每个节点对自身发布的域名在本地计数 1（节点级计数器，防同节点重复发布投毒）。
2. **回执聚合:** 节点发布域名时通过 `count` 泛洪包向好友链扩散，好友回执（`answer` 类回传）聚合累计计数（跨节点计数）。
3. **全网累计:** 全网累计计数 = Σ（各节点本地计数 + 回执聚合），由多点协商共识（§4）达成一致。

**依据:** 节点 02 篇当前无此实现，本结论为协议新增；选「本地计数 + 回执聚合」而非「纯本地计 1」是为了让全网计数可在阈值验证时多点交叉核验（防单点伪造计数）。

### 2.2 count payload 字段（wire 归 T1，语义归本文件）

```
{
  "counter_value": <整数, 节点本地计数值或回执聚合累计值>,
  "timestamp": <Unix 秒, 计数生成时间>,
  "consensus_flag": <bool, false=计数中, true=已达共识阈值触发开关>,
  "vdf_proof": <Base64URL | null, VDF 预留位, 见 §6, 当前恒为 null>
}
```

- `counter_value`: 单调递增（同节点），跨节点由回执聚合累计。
- `consensus_flag`: 计数期恒为 `false`；达 1000 万阈值且多点协商达成共识时间戳后置 `true`，触发开关传播（§5）。
- `vdf_proof`: **预留位**（§6），当前恒 `null`，VDF 机制暂存待用（§0 决策）。

### 2.3 配额计入

`count` 包计入发起节点的**每日用户自主泛洪配额**（T1 §8，每日 3 次，超限 -127）；与 `publish` 共享配额池。系统类（`announce`/`query`/`answer`）不计入。

## 3. 1000 万阈值验证

### 3.1 阈值

- **全网累计计数达 1000 万（10^7）** → 触发多点协商共识时间戳（§4）。
- 阈值固定，不动态调整（防被操纵降低门槛）。

### 3.2 验证规则

| 规则 | 说明 |
|---|---|
| **多点交叉核验** | 任一节点宣称达阈值时，须有 ≥N 个独立节点（N 由多点协商定，草案建议 N=2/3 多数）的回执聚合累计 ≥ 1000 万 |
| **签名防伪造** | count 包签名（T9 覆盖范围含 `forward_chain` + 计数字段）防伪造计数 |
| **去重防重放** | 同 `query_id` + `nonce` 二次计数丢弃（T1 §5.2 + T9 §9.3.1 一次性约束） |
| **拉黑节点不计** | T3 黑名单（-127）节点的计数回执**不计入**累计（防恶意节点灌水） |

### 3.3 阈值未达的行为

计数期（`consensus_flag=false`）内：count 包正常泛洪聚合，节点正常累计；未达阈值前不触发开关。

## 4. 多点协商共识时间戳

### 4.1 共识时间戳的作用

- 计数达 1000 万阈值后，全网节点通过**多点协商**达成一个**共识时间戳 `T_consensus`**。
- `T_consensus` 作为**发布时序裁定依据**（§0 VDF 决策）：后续域名发布以 `T_consensus` 为基准裁定时序（用户裁定，非自动裁决）。
- `T_consensus` 也是**开关触发的时刻标记**（§5）。

### 4.2 共识达成（拜占庭容限）

- **多点协商:** 节点间交换计数累计 + 本地时间戳，达成多数一致（草案建议 ≥2/3 节点一致，拜占庭容限 f < n/3）。
- **最终一致:** 允许短暂不一致（网络延迟），通过泛洪收敛；最终全网收敛到同一 `T_consensus`。
- **防分叉:** 若多点协商无法达成 2/3 多数（拜占庭节点过多），**fail-closed 不触发开关**（计数继续，等待更多节点上线）—— 守安全 fail-closed 红线。

### 4.3 共识时间戳字段

共识达成后，节点在 count 包或独立的 `consensus_announce` 包中广播：

```
{
  "consensus_timestamp": <T_consensus, Unix 秒>,
  "threshold_met": true,
  "participant_count": <参与多点协商的节点数>,
  "signature": <Ed25519, 引用 T9>
}
```

## 5. 开关传播（计数关闭后永不返回）

### 5.1 开关语义

- 共识时间戳 `T_consensus` 达成后，全网开启**计数关闭开关（switch=OFF）**。
- **开关语义:** `switch=OFF` 后，节点**永不返回 count 包**（不再发送、不再响应 count、不再累计）。
- **单向性:** 开关是**单向的**（ON→OFF），一旦关闭永不重新开启（防回退投毒）。
- **接管:** 开关 OFF 后，防污染由运营期信任权重（T3）接管。

### 5.2 开关传播（最终一致）

| 规则 | 说明 |
|---|---|
| **泛洪传播** | 开关 OFF 状态通过 `consensus_announce` 泛洪传播（沿好友链，TTL ≤6，受 forward_chain/fanout 约束） |
| **持久化** | 节点本地持久化 `switch=OFF` 状态（重启不丢失，防重启回退） |
| **拜占庭容限** | 少数拜占庭节点拒绝传播开关 OFF → 被多数节点 isolate（不响应其 count，因全网已 OFF） |
| **最终一致** | 允许短暂不一致（部分节点未收到），通过后续泛洪收敛到全网 OFF |

### 5.3 Fail-closed 默认值

- **默认值显式标注:** 节点启动时若未知开关状态 → **默认 switch=ON（计数中）**（保守，继续计数防投毒）；已知 switch=OFF → 永不返回 count。
- **冲突处置:** 节点收到矛盾的开关状态（部分 ON 部分 OFF）→ **以共识时间戳 `T_consensus` 为准**（有 `T_consensus` 即 OFF），fail-closed 倾向 OFF。

## 6. VDF 预留位（不定型）

### 6.1 当前状态（暂存待用）

- VDF（Verifiable Delay Function）机制 **v3 暂存待用**（§0 决策）—— 共识时间戳保留作为发布时序裁定依据（用户裁定），**VDF 算法暂不引入**。
- count payload 的 `vdf_proof` 字段为**预留位**，当前恒 `null`。

### 6.2 预留目的（方向驱动，分阶段细化）

- 未来若需**强时序保证**（防共识时间戳被提前/延后操纵），可启用 VDF：节点对 `T_consensus` 计算 VDF proof，验证方校验 proof 证明时间戳经过了真实延迟计算。
- **不定型:** VDF 算法选型（如 VDFs based on repeated squaring / class groups）、参数（延迟时长）**不在本草案定型**，守「方向驱动、分阶段细化」红线，留波 2+ 预研。

### 6.3 不越界

- VDF 算法参数定型归 P-ARCH（涉及密码学选型）；本文件仅预留字段位 + 声明用途，不定型实现。

## 7. 时序自洽性（无死锁/无永久阻塞）

### 7.1 计数→阈值→共识→开关时序

```
[引导期] 节点发布域名
   │
   ├─ count 包泛洪（T1 信封，TTL/fanout/forward_chain 约束）
   │     │
   │     ├─ 各节点本地计数 + 回执聚合
   │     └─ 拉黑节点不计 / 签名防伪 / query_id+nonce 去重
   │
   ├─ 全网累计 ≥ 1000 万？
   │     │
   │     ├─ 否 → 继续计数（无阻塞，节点正常运营）
   │     └─ 是 → 多点协商共识时间戳 T_consensus
   │              │
   │              ├─ 多数（≥2/3）一致？
   │              │     │
   │              │     ├─ 是 → 开关 OFF（永不返回 count）→ T3 信任接管
   │              │     └─ 否 → fail-closed，计数继续（不触发开关，等待收敛）
   │              │
   │              └─ （无死锁：少数拜占庭不阻塞多数，多数达成即 OFF）
   │
   └─ [运营期] switch=OFF，T3 信任权重防污染
```

### 7.2 无死锁保证

- **计数期无阻塞:** 未达阈值时节点正常运营（announce/query/answer/publish 照常），count 仅是并发累加。
- **多点协商无永久阻塞:** 若 2/3 多数无法达成（拜占庭过多），fail-closed 继续计数等待节点上线，**不永久阻塞**运营期（其他协议功能不受影响）。
- **开关单向无回退:** OFF 后永不 ON，防回退投毒，时序单调。
